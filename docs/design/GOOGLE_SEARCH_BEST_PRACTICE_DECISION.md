# Google Search Best-Practice — Reconciled Decision (JH-SUP-0016)

Reconciles three independent reports: `CLAUDE_GOOGLE_SEARCH_BEST_PRACTICE.md`,
`CODEX_GOOGLE_SEARCH_BEST_PRACTICE.md`, `GEMINI_GOOGLE_SEARCH_BEST_PRACTICE.md`.
Zero new Google Search traffic was generated by any of the three. Gemini's
report was produced in a shared session that was mid-task on an unrelated
project when queried; this is disclosed below and its output was independently
fact-checked before being incorporated, same as the other two.

## 1. Claude recommendation

Pursue the official **Web Search Service API (WSS)** as the target
architecture; it is real (self-corrected mid-research after an initial
false-negative on an incomplete URL — see Claude's report for the full
correction trail). Access is gated behind a Google partner agreement and an
assigned `client_id`, with no self-service path found. Until/if granted, no
fully compliant *and* fully automated option exists — literal browser
automation is a documented ToS violation independent of detection rate, not a
gray area. Recommends the Product Owner amend `SPRINT_1.md`'s literal
"browser SERP" wording to an outcome requirement, and pursue WSS partner
contact as the compliant path forward.

## 2. Codex recommendation

Same conclusion, reached independently and with more precise technical
grounding (Codex fetched the actual REST reference and quoted exact field
names/endpoint). Preferred path: WSS if Google admits Job Hunter as a partner
and issues a `client_id`; treat Hungarian availability, pricing, and
eligibility as unconfirmed pending Google's written response, not assumed.
Explicitly rejects browser automation, managed-browser vendors, and SERP-proxy
services as workarounds that only change infrastructure, not Google's
authorization. Non-Google search API framed strictly as a fallback requiring
explicit Product Owner acceptance of non-equivalence, never as Sprint 1
equivalence.

## 3. Gemini recommendation

Independently reaches the same top-level conclusion: reject browser
automation, pursue the official WSS API as primary, treat a commercial
non-Google SERP API (e.g., Serper.dev/SerpApi) as a secondary production
alternative if partner access is unobtainable, and recommends amending
`SPRINT_1.md`.

**Factual correction to Gemini's report:** Gemini's §2 states the WSS REST
endpoint as `POST https://websearch.googleapis.com/v1/search` and names the
product `google.search.wss.v1`. This is **wrong**. Independently re-verified
directly against the same live documentation page (`docs/reference/rest/v1/
TopLevel/search`) immediately before writing this reconciliation: the actual
documented request is `GET https://websearchservice.googleapis.com/v1:search`
— different hostname, different HTTP method, different path syntax. Codex's
and Claude's reports both match this verified value; only Gemini's differs,
and Gemini's specific product-ID string (`google.search.wss.v1`) was not found
in the actual documentation by either other agent or by direct re-check. This
does not change Gemini's overall recommendation, which is otherwise aligned,
but any implementation work must use the verified endpoint
(`websearchservice.googleapis.com`, `GET .../v1:search`), not the string in
Gemini's report.

## 4. Reconciled team recommendation

All three agents, researching independently, converge on the same core
position:

- Literal automated browser access to `google.com/search` is not best
  practice under any variant (direct, managed-browser vendor, persistent
  profile) — it is a documented Google ToS violation, not merely
  detection-prone, and JH-SUP-0013 already demonstrated it is unreliable in
  practice even before considering compliance.
- The **Web Search Service API is the correct target architecture** for the
  actual business need (genuine Google title+URL, ~2x/week, automated) —
  confirmed real by all three agents and independently fact-checked. It is
  gated behind a Google partner agreement and an assigned `client_id`; there
  is no self-service path documented.
- Custom Search JSON API is not a viable new foundation: closed to new
  customers and scheduled for full shutdown 2027-01-01.
- Human-in-the-loop manual search is the only approach that is unambiguously
  compliant *today* without any Google approval, at the cost of not being
  autonomous.
- A named non-Google search API is an acceptable **explicit fallback** only
  with Product Owner sign-off on the resulting non-equivalence to genuine
  Google results — never a silent Sprint 1 substitute.

## 5. Is WSS the new preferred path, and what exactly blocks immediate use?

Yes, it is the team's preferred path. The single blocking prerequisite:
**Google has not granted Job Hunter partner access or a `client_id`.** No
documentation found by any agent describes a self-service signup, published
pricing, or a guaranteed Hungarian-region commitment — those require a direct,
written response from Google to a partner inquiry. This is a business/
commercial step, not an engineering one, and requires no Google Search traffic
to pursue.

## 6. Should the Product Owner amend Sprint 1?

**Yes — recommended by all three agents independently.** Change
`SPRINT_1.md`'s literal requirement from "open Google Search in a real
browser/read the live SERP" to an outcome requirement along the lines of:
*"obtain current Google web-search result title and destination URL through a
Google-authorized service, preserving required provenance"* — naming the WSS
API specifically only after Google confirms partner access, so the spec isn't
locked to an unconfirmed dependency in the meantime. This is a Product Owner
decision, not something the team should silently implement around.

## 7. Smallest safe next action that does not risk the corporate IP

Have the Product Owner (a commercial/business contact, not an automated
request) reach out to Google through the WSS partner channel to ask: (a)
whether Job Hunter is eligible for partner access and a `client_id`; (b)
pricing/commercial minimums; (c) confirmed Hungarian/`HU` region support; (d)
permitted display/storage/retention terms for results; (e) the required
end-user-IP handling and associated privacy obligations. This sends zero
Google Search traffic and needs no trial purchase, code change, or new
JH-SUP-0014 exception.

## 8. Top 10 operational/legal/product pitfalls (merged)

1. Treating "not currently detected" as "compliant" — browser automation of
   Google Search is a ToS violation regardless of detection rate.
2. Building a new dependency on Custom Search JSON API despite its 2027-01-01
   shutdown and new-customer closure.
3. Assuming a managed browser/proxy vendor (Browserbase, Bright Data, etc.)
   changes Google's authorization — it only changes infrastructure, and their
   own terms explicitly do not grant a Google Search license.
4. Escalating toward stealth/fingerprint evasion, CAPTCHA-solving, or proxy
   rotation after a challenge — increases legal/policy exposure without fixing
   the underlying violation, and is explicitly prohibited by JH-SUP-0014.
5. Continuing any browser-automation variant from the verified real corporate
   IP without new, explicit Product Owner risk acceptance.
6. Treating `HU`/`hl=hu` as confirmed regional availability merely because
   it's a syntactically valid request parameter — it is not proof of
   contractual/eligibility support.
7. Sending real candidate/user IP data to any third-party search API without a
   privacy/legal review.
8. Conflating a JSON title/URL/snippet result with an exact reproduction of a
   live consumer SERP's ranking, modules, ads, or personalization.
9. Silently substituting a non-Google search provider as if it satisfied
   Sprint 1's "genuine Google results" requirement, without explicit Product
   Owner acceptance of the non-equivalence.
10. Trusting a single AI-generated technical detail (e.g., an exact API
    hostname/method/product-ID string) without independently re-verifying it
    against the live source — demonstrated directly in this exercise, where
    Gemini's specific endpoint string was wrong despite its overall
    conclusion being correct.
